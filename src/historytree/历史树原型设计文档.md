# 历史树原型设计文档

## 一、背景与目标

### 	1.背景——用户痛点

​		在使用cad的时候，我们往往需要进行很多步的建模操作。正所谓马有失蹄，人有失足，我们可能会在前面的某一个步骤遗漏了一些操作，这时候我们希望去回到那个时间节点去查缺补漏，这在一般的cad中是允许的。但是在solvespace的使用中，这却是一个缺失的功能——我们不能进行“时间回溯”，只能在当前步骤上增删查改，所以我们希望在solvespace中添加此类功能。

​		所以对于solvespace的现状，我们希望首先添加一个功能——对建模步骤的顺序进行更换。

### 	2.目标——给ss添加简单的历史树功能

​		在历史树中，最简单、最基础的功能就是，我已经做了一些组的操作步骤，现在希望交换组的位置。

​		例如说：

​		![](D:\work\toys\01SolveSpace\solvespace\src\historytree\picture\示例图.png)

​		现在在每个组的右边，我们希望对每个组都可以进行以下操作。

​		向上的箭头是希望把这个组向上移动一个位置，如果能移动就皆大欢喜，不能就会弹出一个警告：你不能这样移动该组！因为XXX（例如该组已经是最上面的组了！/该组依赖于上面的XXX组！不能置于它之上）。

## 二、现有逻辑说明

### 	1.关于solvespace的原生历史树

​		关于solvespace的原生历史树，其实是异常简陋的，或者甚至说它都没有历史树这一设计。它有的只是全局变量SK下的group和groupOrder两个数组。前者group数组会存放建模中产生的组，而每个组又会有它的id句柄h.v、建模顺序order、依赖组OpA、依赖实体predef这四个关键构成以及其他数据，groupOrder则简单的多，仅仅是存放执行到哪个组而已。

## 三、方案选型 & 新功能原理

### 	1.方案选型

​			（1）新增历史树组件

​				solvespace本身的重要组件只有UI管理器的SolveSpaceUI，和存放建模数据的Sketch，缺少一个历史树管理器。所以该方案计划添加一个与它们具有同等地位的历史树管理器HistMgr。它作为一个类存在，可以读取Sk底下的group和groupOrder数据，并进行修改，比如选中一个组，可以让他往上移动，或者往下移动。

​			（2）添加组移动函数

​				solvespace的全局变量Sketch下，我们可以添加对于group成员的管理函数。当ui组件触发后就会调用这里的往上移动或者往下移动的函数，其实有与方案一中的函数具有同等功能。

​			（3）SK暴露组的修改接口，**HM**（HistMgr）调用SK的接口，UI组件调用HM

​				这个方案其实是方案一二的中间取舍，是在方案一二先出来之后权衡得出的方案。	

### 			最终选型

​				最后，我认为选择方案三。

​				为什么不选择方案一？因为方案一让HM读取SK的数据、判断能否移动和再修改SK的数据。这一行为会导致双写者问题——你不能让两个组件修改同一处数据，谁创建的数据，就应该由谁来修改，至于其他组件，可读即可。

​				为什么不选方案二？因为方案二会导致高耦合的问题，并且扩展性太差了。对于SK，从目前的定义看来，功能只是对模型数据的存储和修改，不应该还有着历史树的功能。况且如果不添加HM，那么日后历史树相关功能的扩展都会放在SK里面，那么SK的功能就很多很杂，不好后续维护。

​				所以权衡之下选择方案三。

### 	2.该方案原理

​	主要有三步。

​	1.SK下实现接口Up和Down，使其能够被外部调用去修改组的顺序

​	2.HistMgrProtype，去调用SK的接口

​	3.每个组右侧都有上移下移的UI按钮，UI按钮会去调用HM，修改完数据进行重生成，从而达到交换组的效果

## 四、组件详细设计

### 		1.SK下的接口

​		SK 是移动规则与判据的唯一拥有者。新增三样东西：错误码枚举、校验接口、移动接口。

​		（1）错误码枚举

​		枚举定义在 SK 侧（sketch.h），不能放在 HM 下——否则 SK 的接口返回类型要引用 HM 的类型，造成模型层反向依赖控制器层。HM 只负责把枚举翻译成提示文案。

```c++
enum class MoveDir { UP, DOWN };

enum class MoveErr {
    OK,                   // 可以移动
    NO_SUCH_GROUP,        // 组不存在
    AT_TOP,               // 已经在最上面
    AT_BOTTOM,            // 已经在最下面
    IS_REFERENCE,         // 参考组（HGROUP_REFERENCES，order 0）不可移动
    DEPENDS_ON_NEIGHBOR   // 依赖相邻组，交换会破坏生成顺序
};
```

​		（2）校验接口（纯检查，不改数据）

```c++
MoveErr Sketch::CanMoveGroup(hGroup hg, MoveDir dir) const;
/***
hg  表示希望移动的组的句柄
dir 表示希望移动的方向
返回 OK 表示可以移动，否则返回对应错误码
***/
```

​		判据，按顺序检查：

- 组存在性、首尾边界（第一个组不能上移、最后一个组不能下移）、参考组不可移动
- 依赖校验：相邻交换只改变这一对组的相对顺序，所以**只检查"向上移动的组是否引用了向下移动的组"**，不涉及第三组。需要覆盖的引用面：`opA/opB`、`predef.origin/entityB/entityC`、该组 `Request::workplane`、该组 `Constraint` 的 `workplane/ptA/ptB/entityA-D`
- 实体归属用 `SK.GetEntity(he)->group` 解析，不能用 `hEntity::group()`——后者对 request 生成的实体拿到的是 request index，不是组
- 有序表从 `SK.group` 现算，不读 `SK.groupOrder`——它是 `GenerateAll` 每次重建的派生缓存，可能过期

​		（3）移动接口（校验+修改一体）

```c++
MoveErr Sketch::MoveGroup(hGroup hg, MoveDir dir);
/***
内部先调用 CanMoveGroup 校验：
- 失败则不改任何数据，原样返回错误码
- 成功则交换相邻两项，并重编号
***/
```

​		成功时做的事：

1. 从 `SK.group` 构建有序表，交换相邻两项
2. 整体重编号 `order = 0..n-1`（不能只交换两个 int，文件里的 order 可能有空洞或重复）
3. 同步更新 `SK.groupOrder` 为新顺序

### 	2.HistMgr的设计

​		（1）成员

​				暂无，当作无字段的函数集合。

​		（2）函数

```c++
class HistMgr {
public:
    static void MoveUp(hGroup hg);
    static void MoveDown(hGroup hg);
private:
    static void Move(hGroup hg, MoveDir dir);   // 唯一核心
    static const char *MoveErrText(MoveErr e);  // 唯一的错误码→文案映射
};
```

​		注意调用方向：public 的 `MoveUp/MoveDown` 是两行薄封装，内部调用 private 的 `Move` 核心；不能让 `Move` 反过来调用 `MoveUp/MoveDown`。邻项查找、校验、重生成逻辑只写一份。

​		（3）`Move` 的固定事务顺序

```
SK.CanMoveGroup(hg, dir)
  失败 → MoveErrText 翻译错误码 → Error(...) 弹窗提示原因，结束（不压 undo）
SS.UndoRemember()            // 必须在修改之前压栈
SK.MoveGroup(hg, dir)        // 内部再校验一次，防御性
SS.GenerateAll(Generate::ALL)
SS.GW.ClearSuper()
SS.ScheduleShowTW()
```

​		要点：

- **先校验再 Undo**：反过来的话失败会往 undo 栈压一个无变化的快照
- **原型用 `Generate::ALL`**，不用 `DIRTY`：DIRTY 的求解范围由 activeGroup 决定，交换后"哪些组脏了"需要重新推理，原型不值得承担这个复杂度
- **不调 `MarkGroupDirty`**：它遍历的是 `SK.groupOrder` 缓存，和上面同一个坑；`GenerateAll(ALL)` 已经把全部组重新求解了
- 错误文案集中在 `MoveErrText` 一处，以后加错误码只动这个函数
- HM 不读 `SK.group`/`groupOrder` 做判断，不直接改 SK 数据，只做编排、翻译、弹窗

### 	3.UI组件的设计

​		不做工具栏按钮（要改 Command 枚举、菜单文案表、图标资源，原型不划算）。就做在文本窗口的组列表里——`TextWindow::ShowListOfGroups()`（textscreens.cpp），它每行已经挂了 4 个链接（激活、显示切换、求解信息、组详情），加两个箭头就是再加两个链接。

​		改动点 1：ui.h 中 `TextWindow` 的回调声明区加两个：

```c++
static void ScreenMoveGroupUp(int link, uint32_t v);
static void ScreenMoveGroupDown(int link, uint32_t v);
```

​		改动点 2：textscreens.cpp 中 `ScreenActivateGroup` 旁边加实现。函数体要极薄，只调 HM，不碰 SK；刷新、再生、undo 全部由 HM 负责：

```c++
void TextWindow::ScreenMoveGroupUp(int link, uint32_t v) {
    HistMgr::MoveUp((hGroup){v});
}
```

​		改动点 3：`ShowListOfGroups` 的行格式串里，每行追加两个链接。格式机制：`%L`+字符 设置链接 id，`%D` 设置点击回传的 uint32_t（不打印字符），`%f` 设置回调函数，`%E` 清空链接状态：

```
"%Fp%D%f%Ll%s%E%D%f%Ld%s%E"
    g->h.v, &TextWindow::ScreenMoveGroupUp,   "<",
    g->h.v, &TextWindow::ScreenMoveGroupDown, ">"
```

​		设计规则：

- 两个链接的字符必须不同（`%Ll`/`%Ld`），否则相邻同函数同数据的字符会被合并成一条下划线
- 箭头字符用 `<`/`>` 或 `^`/`v`，别用 `↑↓`——文本窗口用位图字体，没有这些字形
- 箭头放行首，避免长组名把箭头挤出 `MAX_COLS=100` 的行宽
- 参考组（`ref` 行）不显示箭头
- 箭头永远可点、不做置灰：点不动时由 HM 弹原因，否则用户得不到"为什么不能移"的提示

​		整体数据流向是单向的：

```
点箭头 → ScreenMoveGroupUp/Down（UI，薄壳）
       → HistMgr::MoveUp/Down（编排：校验、undo、弹窗、刷新）
       → SK.CanMoveGroup / SK.MoveGroup（规则+数据）
       → GenerateAll 重建 groupOrder → 文本窗口刷新显示新顺序
```
